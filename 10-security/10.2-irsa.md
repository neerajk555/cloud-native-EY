# Lab 10.2: IAM Roles for Service Accounts (IRSA)

**Cost:** ✅ Free (shared cluster)
**Time:** ~15 min

## Objective

Give a pod in your namespace S3 read-only access via the pre-created, OIDC-federated shared IRSA role — no role creation required.

## Prerequisites

- Module 4 complete
- `$PARTICIPANT` is exported for this session (see `SETUP-UBUNTU.md`)

## Steps

### Step 1: Create a service account in your namespace bound to the shared role

```bash
irsaRoleArn=$(aws iam get-role --role-name course-irsa-s3-readonly --query Role.Arn --output text)
eksctl create iamserviceaccount --cluster course-shared-cluster --name irsa-demo-sa --namespace ns-$PARTICIPANT --role-arn $irsaRoleArn --override-existing-serviceaccounts --approve
```


### Step 2: Run a pod using that service account

```bash
kubectl run irsa-test-$PARTICIPANT --image=amazon/aws-cli -n ns-$PARTICIPANT --overrides='{"spec":{"serviceAccountName":"irsa-demo-sa"}}' --command -- sleep 3600
```


### Step 3: Test S3 access from inside the pod

```bash
kubectl exec -n ns-$PARTICIPANT irsa-test-$PARTICIPANT -- aws s3 ls
```


## Expected Result

The pod can list S3 buckets read-only, without any access key ever being stored in the pod.

## Cleanup

```bash
kubectl delete pod irsa-test-$PARTICIPANT -n ns-$PARTICIPANT
kubectl delete serviceaccount irsa-demo-sa -n ns-$PARTICIPANT
```

## Troubleshooting

- **AccessDenied inside the pod**: The shared role's trust policy uses `StringLike` on `system:serviceaccount:ns-*:irsa-demo-sa` — confirm your service account is named exactly `irsa-demo-sa` in your own `ns-$PARTICIPANT` namespace.
